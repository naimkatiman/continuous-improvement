## [3.28.0] — 2026-11-25

### Added

- **The `be-ambitious` skill and `/be-ambitious` command ship in the bundle, as the first of two pillars (ambition and discipline)**: the package had nothing for big goals. The skill takes one task and works it on three axes (Altitude: the goal behind the task; Depth: the way the best person in the field would do it; Range: other fields doing their real work), fixes a hard numeric target and a judge that can fail before the work starts, does the work, then reports baseline, result and target. It carries its own rules, and they are text too: deliver the literal ask, do not grade your own work, wait for a yes before anything hard to reverse or outward-facing. It is guidance: no hook checks that an agent followed it. It is one flat file with no Claude-only tool names, so `install --target <agent> --hooks` copies it to every agent that reads skills; the slash command is Claude Code's. The method is from Felix Rieseberg's *How to be more ambitious* (13 October 2026), restated (the four depth questions follow the article's) with the skill's own examples and credited in both files. The bundle is now 29 skills and 30 commands, and every count (manifests, README, `docs/skills.md`, landing, the dry-run demo image) says so. `summarize()` in `lib/skill-catalog.mjs` strips a `Guidance for Law N` preamble as it does `Enforces Law N`. Decision record: `docs/plans/2026-11-25-two-pillars.md`.

- **The hooks now answer each agent in the format it reads, so a deny blocks on Gemini, Cursor, Copilot, Devin, Kiro CLI, Goose and Cline too, and on Junie's Early Access build** — `lib/hook-io.mjs` gains an encoder for each of the thirteen other agents the 2026-11-21 research verified. A deny is the Claude `hookSpecificOutput.permissionDecision` JSON on Codex, Qwen, Grok, Droid and Auggie, top-level `{decision:"deny",reason}` on Gemini, `{permission:"deny",user_message,agent_message}` on Cursor, top-level `permissionDecision` on Copilot, `{decision:"block",reason}` on Devin, `{cancel:true,errorMessage}` on Cline, and exit 2 with the reason on stderr on Kiro, Junie and Goose. Session lessons go out as plain stdout (Codex, Qwen, Droid, Kiro), `hookSpecificOutput.additionalContext` (Gemini, Devin), `additionalContext` (Copilot, whose camelCase `sessionStart` names no event, so session.mjs reads it as SessionStart by its `source` of `startup`, `resume` or `new`), `additional_context` (Cursor) or `contextModification` (Cline); Grok, Auggie, Junie and Goose have no verified context channel and get nothing on stdout. A Stop continue is `{decision:"block"}`, `{decision:"deny"}` on Gemini and `followup_message` on Cursor. An allow is empty stdout and exit 0 for every agent. A hook picks its agent from `--agent <id>`, then `CI_AGENT`, then a sniff that needs both an agent env var and that agent's payload shape (Cursor, Gemini, Devin, Grok, Qwen), and otherwise answers as Claude Code. A payload that is clearly not Claude's but matches no sniff, and an empty or unknown `--agent` value, get exit 2 with the reason on stderr, so a misdetection never turns a deny into an allow. On such a payload only the Cursor and Gemini sniffs, whose shapes are themselves non-Claude, can name the agent, so a stray `QWEN_PROJECT_DIR` or `DEVIN_PROJECT_DIR` in a Goose or Cline hook leaves the deny at exit 2. The Gemini sniff also fires on Gemini's `SessionStart` and `SessionEnd` (a string `timestamp`), and the Devin sniff on Devin's `SessionStart` (`source` `startup` or `resume`, no `transcript_path`), so the lessons reach the model there too. New `src/test/agent-matrix.test.mts` runs every wired hook against `fixtures/agent-matrix/<agent>.json` for all fourteen agents (each payload with its source, the date checked and its unverified keys) and checks the deny, the empty allow and the session context per agent. - **Every hook and the observer now find the same store and project from any agent's environment, and take CI_* names for the CLAUDE_* knobs** — new `lib/agent-paths.mjs` replaces the ten copies of the project-root resolver and the instincts-root joins in the hooks, `bin/observe.mjs` and `lib/gateguard-state.mjs`. The store stays `<home>/.claude/instincts` unless the new `CI_INSTINCTS_HOME` names another absolute directory (a relative value is ignored, since each process would resolve it against its own cwd). The old names keep working, and when both are set to a non-blank value the CLAUDE_* name wins, so an existing Claude Code setup behaves exactly as before. Every golden that sets a knob is replayed under its alias with the same bytes, and once per knob with the alias set to `off` beside the CLAUDE_* value. - **The MCP server and the offline CLIs use the same store and project as the hooks** — `bin/mcp-server.mjs`, `bin/backfill.mjs`, `bin/harvest-friction.mjs`, `bin/companion-preference-status.mjs` and the installer's pack and update-check data now resolve the store through `lib/agent-paths.mjs`, so they follow `CI_INSTINCTS_HOME` like the hooks. `companion-preference-status` drops its own resolver and reads the other agents' project env vars too. The MCP server no longer splits its project in two: `getWorkspaceRoot` (git toplevel, else cwd) is gone, and the planning tools (`ci_plan_init`, `ci_plan_status`, `ci_goal_check`) use the root that picks the instincts bucket when it is an absolute, existing directory, and otherwise the git toplevel of the server's cwd, then the cwd. A project env var such as `CLAUDE_PROJECT_DIR` is still taken as given for the bucket, but when it names a path that does not exist (or a relative path, or a file) the planning files go where the old `getWorkspaceRoot` put them, so `ci_plan_init` no longer fails with ENOENT on a synthetic env root. When the env var names an existing directory that differs from the server's git toplevel, the planning tools now use that directory; for Claude Code that applies only if it passes `CLAUDE_PROJECT_DIR` to MCP servers, which the 2026-11-21 research does not establish. On Windows the old `getWorkspaceRoot` ran `git ... 2>/dev/null` under cmd.exe, always failed and fell back to the cwd, so a server started in a repository subdirectory there now uses the repository toplevel, as it already did on Linux and macOS. When the MCP client declares the `roots` capability, the server sends `roots/list` after `notifications/initialized` and again on `notifications/roots/list_changed`, and the first `file://` root of the latest reply counts like a hook payload `cwd` when it is inside a repository (taken as its toplevel). Only that first file root is tried, like the hooks' `workspace_roots[0]`, so a multi-root client that lists a non-repository folder first gets the server's cwd even when a later root is a repository. So for an agent that sets no project env var and starts the server outside its repository, the bucket, the planning files and the `ci_gateguard_clear` fallback match what its hooks resolve. A project env var still wins, a reply with no usable root falls back to the cwd, a stale or unknown reply is ignored and never answered, and a client without the capability gets no request. The installer's knob `CLAUDE_CI_UPDATE_CHECK` also answers to `CI_UPDATE_CHECK`, and the CLAUDE_* value wins when both are set.
